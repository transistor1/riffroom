# Validation · 2026-09-18

Test machine: Apple M1 MacBook Air, 16 GB memory, macOS 27.0. Python 3.11.16 in the project-local environment. MLX 0.31.2, mlx-audio-separator 0.1.7, Torch/Torchaudio 2.8.0, Demucs 4.0.1. FFmpeg 8.1.1. Frontend built with React 19 / TypeScript / Vite 6.

## Demucs cache regression discovered and fixed

The first smoke tests were insufficient: they checked inference completion and
file alignment, not whether cached Demucs tensors were actually restored. A
user's real-song report exposed buzzy, nearly unseparated results.

`mlx-audio-separator` 0.1.7 exports native MLX parameter paths (for example,
`encoder.0.conv.conv.weight`), then reloads them using a Torch-name mapping that
strips wrappers. In the six-stem cache, 352 of 565 tensors differed from the saved
weights after the original loader returned. Most of the model was therefore
left initialized rather than restored. This is a runtime cache-loading bug,
not a conclusion about Demucs's separation quality.

Riffroom now restores native cache keys with `load_weights(..., strict=True)`
after upstream hash/config validation and before inference. Both six-stem and
fine-tuned model caches pass a GPU regression that compares every loaded tensor
to disk and requires incomplete caches to fail.

On an eight-second excerpt of the user's song, repaired six-stem MLX outputs
matched original PyTorch Demucs to less than 0.03% relative L2 error for every
stem. The relative reconstruction error dropped from about 1.005 for the broken
saved result to 0.1082, matching original Demucs (0.1082). Reconstruction error is
not an instrument-isolation quality score; the near-identical reference outputs
are the meaningful runtime check.

Run the tensor regression with:

```bash
RIFFROOM_MLX_TESTS=1 .env/bin/pytest backend/tests/test_demucs_cache.py -q
```

Run a local audio comparison with:

```bash
.env/bin/python scripts/check_demucs_parity.py path/to/stereo-44100.wav
```

Old outputs are not repaired by changing the loader; they must be separated
again. New jobs use the fix without restarting the server because inference
runs in a fresh worker process. RoFormer inference is unchanged.

Output frame counts must match the source before the app publishes results.

## Known limits

- No lead/rhythm role separation; every included guitar model returns all guitars together.
- Speed changes pitch; no pitch-preserving time-stretch engine yet.
- Browser buffers hold the selected result in memory. Large tracks use substantial RAM.
- Loop points and transport state reset on result changes; saved channel mix levels/mutes/solos survive browser reloads.
- Automated browser testing used desktop Chrome. Safari audio decoding was not separately tested.
- Separation is approximate and can leak instruments. The synthetic test does not establish which model sounds best on a particular recording.

## Cross-platform source launcher MVP

Start from a writable checkout (paths containing spaces are supported):

- Apple Silicon macOS: double-click `Riffroom.command`, or run `bash start.sh`.
  Diagnostics: `bash start.sh --check` (also `bash scripts/setup.sh --check`).
- Linux: run `bash start.sh`; diagnostics: `bash start.sh --check`.
  Install Python 3.11–3.13 including venv/pip support, Node.js 22+ with npm, and
  FFmpeg/ffprobe using your distribution's documented instructions first.
- Windows: from PowerShell in the checkout, run
  `powershell -NoProfile -ExecutionPolicy Bypass -File .\Riffroom.ps1`.
  The policy override applies only to this invocation. Respect organizational policy restrictions.
  Add `-Check` for diagnostics or `-NoBrowser` for headless startup.
  Install Python 3.11–3.13 (Python launcher or PATH option), Node.js 22+ with npm, and
  FFmpeg with both ffmpeg.exe/ffprobe.exe on PATH; reopen the terminal afterward.
  Existing Conda users may optionally obtain Node.js/npm and FFmpeg/ffprobe from Conda. Conda is not
  required, and Riffroom does not create or manage a Conda environment.
  `start.ps1` is also a direct entry point. No administrator shell is required.

The launchers create/reuse `.env` automatically. Do not copy `.env` between OSes or machines;
if diagnostics report an incompatible environment, move it aside and rerun. Setup downloads
pinned core packages and frontend dependencies; network access is required on first run.
No outer launcher installs the managed separation runtime. Node/FFmpeg must remain on PATH. When those
tools come from an activated Conda environment, that environment may need to remain activated while Riffroom
runs. Conda then supplies host executables, while Riffroom's Python packages and application interpreter remain
in the project-local `.env`; Riffroom does not merge or manage the environments.
`--check`/`-Check` return nonzero for missing/incompatible prerequisites and report a missing or
stale build/stamp as "setup required" without making changes.

## Optional Windows CUDA runtime · 2026-10-11 / live follow-up 2026-10-13

Windows x86-64 managed installs now use the fixed `audio-separator[gpu]==0.47.0`,
`torch==2.8.0+cu128`, `torchvision==0.23.0+cu128`, `torchaudio==2.8.0+cu128`, and
`onnxruntime-gpu==1.23.2` recipe. The same wheels remain CPU-capable when
`torch.cuda.is_available()` is false. Windows ARM64 and every non-Windows recipe are unchanged.
The pinned audio-separator CLI has no CUDA flag; its own 0.47.0 device setup automatically chooses
CUDA when Torch reports it available, otherwise CPU. Runtime status probes the selected managed
interpreter once and Model Manager displays the sanitized GPU name plus CUDA, or CPU fallback.

A live Windows x86-64 install on an RTX 4070-class system found that recipe 4 did not preserve this stack.
`nvidia-smi` saw the GPU (driver 610.88, CUDA UMD 13.3), but the managed interpreter reported
`torch==2.14.1+cpu`, `torch.version.cuda is None`, and `torch.cuda.is_available() is False`. The later general
dependency step installed `onnx2torch-py313`, whose `torchvision>=0.9` requirement was unconstrained. Resolving the
newest torchvision selected its exact newer Torch dependency from PyPI and replaced the previously installed CUDA
wheel. Recipe 5 installs the official matching PyTorch 2.8 CUDA trio together and writes those exact local-version
pins to a constraint file used by both later pip steps. Before publication it imports the trio, checks their exact
versions, and requires non-null `torch.version.cuda`; it deliberately does not call `torch.cuda.is_available()`, so
installation remains valid on Windows hosts without an NVIDIA GPU. Runtime status still calls
`torch.cuda.is_available()` to choose CUDA or CPU fallback. Recipe 4 markers are stale and force reinstallation.

Live Windows follow-up on an NVIDIA GeForce RTX 4070 Ti SUPER confirmed that recipe 5 installs successfully and
Model Manager reports `NVIDIA GeForce RTX 4070 Ti SUPER · CUDA`. Demucs 6 separation completed on CUDA and was
dramatically faster than CPU. MDX23C DrumSep also completed on CUDA while `nvidia-smi` showed sustained 74–81%
GPU utilization, about 2.1–2.2 GB VRAM, and about 200 W. Cancellation during separation also succeeded.

Further live runs on that same Windows CUDA host completed `BS-Roformer-SW.ckpt` end to end with all six logical
stems; observed load was about 3.0 GB VRAM, frequently 100% GPU utilization, and roughly 240–259 W. The
`htdemucs_ft.yaml` detailed four-stem model also completed end to end, using about 1.96 GB VRAM, mostly 75–87% GPU
utilization, and roughly 150–165 W. These observations are valid execution evidence, not failure symptoms, so both

The first `vocals_mel_band_roformer.ckpt` run completed upstream inference, producing `vocals.wav` plus
`original_(other)_vocals_mel_band_roformer.wav`, but Riffroom post-validation still expected `instrumental.wav`.
